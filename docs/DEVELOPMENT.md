## 01 · 起点：先明确要做哪一种桌面程序

项目最初的目标，是分析提供的 APK，把核心短剧业务做成能在 Windows 上独立运行的应用。用户随后不断提出具体体验要求：不要网页套壳、不要模拟器前端、不要打断电脑使用，界面要简洁，视频要尽快显示，选择操作要立即有反馈。

这些要求决定了技术路线：自己编写桌面界面，调用 APK 对应的服务，通过本机适配处理原生能力，而不是把安卓手机界面塞进窗口。

首批优先实现“找到一部剧 → 打开目录 → 播放真实视频 → 记住位置”。小说、听书、社区等共享业务没有被当作已经移植完成的功能。

### 开发中的固定规则

| 规则 | 为什么需要 |
| --- | --- |
| 每个修改批次先备份 | 出现回归时能回到修改前状态，而不只依赖口头记忆 |
| 备份写入时间、版本、范围和 SHA256 | 确认备份包含什么，并能检查文件有没有变 |
| 重大升级保留可运行旧版 | 新版出问题时，仍有可用程序和可比较的资源 |
| 原 APK 与提取目录不改 | 保留研究原始依据，避免分析的是自己修改过的输入 |
| 先调查未知接口，再写计划 | 外观相似的功能可能走不同接口，不能只猜参数 |
| 测试隐藏、静音 | 不抢占用户窗口，不影响正常使用电脑 |
| 不改全局代理、证书和系统主题 | 避免为了让测试通过而改变整台电脑的环境 |
| 保留授权与锁定状态 | 界面优化不能变成取消服务权限限制 |
| 私人身份不进源码和发布包 | 游客、账号、验证码、Cookie、签名与密钥不能成为公开样本 |

## 02 · APK 调查：从“很多代码”里找到真正的业务入口

输入 APK 的包名是 `com.phoenix.read`，版本为 `7.3.9.32 / 73932`。包内不只有短剧，还包含共享小说、听书业务以及大量 SDK。

原始盘点记录了 24 个 DEX、约 31.7 万个索引类和 23,367 个解压文件。这个数量包括生成类、内部类和第三方 SDK，不是 31.7 万个独立业务功能。

研究采用选择性追踪：先从类索引、网络注解和模型找到业务入口，再沿着“页面 → 数据请求 → 请求模型 → 返回模型”核对。这样比把所有代码反编译后逐页翻看更容易得到可用结论。

### 每个功能都要回答三个问题

1. **它向哪个接口请求？** 同名页面可能有旧接口、新接口和不同场景接口。
2. **请求要带哪些上下文？** 分页、分类、排序、游客身份和授权状态不能任意拼接。
3. **返回数据怎样解释？** 一条数据可能是正剧、预告、预约、演员或系列入口，不能全部当作可直接播放的剧。

静态调用链提供方向，真实服务返回负责验证。当返回与预期不同，先确认业务路径，而不是把测试数据改成“看起来成功”。

### 原生适配为什么保留 Java

服务请求需要原 APK 的签名与加密处理。相关库是 Android ARM/JNI 库，不能直接当成 Windows DLL 加载。

本项目用 Java worker 与 unidbg 提供它们需要的局部执行环境，Electron 主进程负责管理调用。这里没有运行完整 Android 系统，也没有把模拟器界面交给用户操作。

公开仓库只包含自行编写的适配器源码；原生库和专有配置需要用户自己准备。这个依赖后来也决定了开源范围与构建说明必须清楚区分。

## 03 · 0.4 与 0.5：从能播放，做到适合连续观看

### 0.4：打通完整的短剧流程

0.4 阶段完成新游客注册、请求签名、首页、搜索、详情、完整目录和真实音视频。界面加入浅色／深色／跟随系统主题，并处理 HEIC 封面显示、本地追剧、历史位置和续播。

当时的 Windows 完整程序做过隐藏启动与真实媒体验证，记录了实际视频尺寸、视频帧和音频解码数据。账号逻辑虽然已经有适配和界面，但初期并没有完整真实账号验收，不能把受控测试写成短信登录成功。

### 0.5：把播放、选集和窗口模式连起来

用户提出要减少视频周围的信息，支持持续刷推荐、最高画质、音量、自动隐藏、保帧跳转和统一选集面板。

| 问题 | 改动 | 需要保护的行为 |
| --- | --- | --- |
| 首页只有一批推荐 | 沿原服务分页继续获取，并保存已访问条目 | 向上滚动回到旧内容，不能每次重新随机排列 |
| 播放控制分散 | 统一清晰度、倍速、音量、进度、下一集与选集 | 保留真实播放回调和设置 |
| 拖动进度时显示封面 | 保留已解码画面，目标帧到达后交接 | 暂停时跳转仍保持暂停，不提前写错误位置 |
| 详情与选集分成两个入口 | 合并为一个详情／选集面板 | 面板滚动不能触发视频切换 |
| 单次滚轮跳过多集 | 增加滚动手势判定与等待保护 | 一次手势只切一次，加载与动画期间不重复触发 |
| 窗口模式含糊 | 分开常规、无边框窗口与全屏状态 | 再次切换能恢复，控制栏状态不混乱 |

推荐的续页位置、会话和容器信息保存在主进程，界面只收到受限标记。推荐与排行不能共用游标，否则看起来“加载更多”正常，实际却可能加载了别的业务。

## 04 · 0.6：针对实际操作逐项修复

### 窗口按钮看得见，但点不动

**表现：** 最小化、最大化和关闭按钮存在，点击没有反应。

**调查：** 按钮与窗口拖动区域的矩形重叠。拖动区域会把鼠标输入作为拖动处理，仅把按钮画在上面不能保证收到点击。

**处理：** 只给独立空白区域拖动能力，按钮、图标、搜索框等明确不参与拖动；窗口操作通过受限 IPC 交给主进程。窗口铺满播放时利用透明顶部区域提供拖动入口，保持外观不增加一条标题栏。

验证了点击通道和隐藏窗口状态；没有为了测试而操作用户的活动窗口。

### 搜索和排行不能停在第一页

搜索联想接入原版 suggest 接口，加入短暂防抖、输入法组合保护、方向键／确认／退出操作，并过滤不适合当作显示词的纯编号。

搜索续页核对原业务调用链，沿上一页返回的 offset、search_id、passback 继续。页面接近底部自动获取，追加时按剧目去重。旧查询失效后，晚到响应不能再次写入新查询。

排行也使用原版会话和续页规则，不把“固定数组滚到底”描述成动态加载。

### 翻动效果为何改了几次

用户反馈推动了连续三步修正：

| 当时的行为 | 为什么不够好 | 最终方向 |
| --- | --- | --- |
| 等目标视频加载好，再翻动 | 点了／滚了之后像没反应 | 手势发生就开始动画 |
| 翻到一半，等目标首帧 | 动画停住，看起来卡住 | 动画连续完成，不等待网络 |
| 新画面没到时仍露出旧视频 | 动画结束后又突然换内容，容易误认 | 旧画面只参与离场；未就绪区保持黑色 |

最终动画使用约 620ms 的连续翻动，节奏比早期更缓和。目标首帧到了就显示并按播放状态继续，不等待整个文件下载。这能改善响应感，但不能把网络等待变成零。

**刷下一条与拖动进度采用不同等待方式。** 刷剧时避免用旧内容冒充目标；同一视频跳进度或换清晰度时，保留操作前已解码画面，避免换成封面。

### 减少不必要的加载界面

正常刷视频时移除“正在准备好剧”等占位提示和封面替身。失败仍保留可理解的错误与重试，不能把持续黑屏当作成功。

排行榜先呈现公开的分类和筛选结构，再用服务实际配置更新，具体剧目仍联网获取。预填的是界面结构，不是伪造榜单、个人身份或过期热度数据。

播放器进度条改为细轨道与小圆点，实际点击区域保持足够高度。视频留白变为纯黑，侧栏与顶部统一背景，去掉多余分界和突兀的外圈。

## 05 · 账号与同步：收到验证码，并不代表已经登录成功

用户曾遇到收到短信但不能登录，之后又出现登录后用户信息或云同步校验失败。这些是不同阶段的问题，不能靠显示“已登录”统一掩盖。

### 登录阶段的发现

服务可能返回多条 Cookie，而通用响应头处理容易丢失或错误拆分它们；Cookie 的 Expires 字段自身也包含逗号。传输层调整为保留原始响应头，解析完整会话，登录失败则回滚局部状态。

备用会话也必须经过真实账号信息确认，不能只看到一个 token 就保存为有效登录。验证码错误、安全挑战与服务拒绝仍明确报错。

### 同步阶段的发现

Passport 的数字用户编号与阅读业务的编码账号字段不是同一种身份表示，直接比较会误判。同步逻辑先核验真实账号，再确认对应阅读身份，沿原版分页读取与上传进度，并检查服务确认。

历史阶段曾在一个既有 Windows 账号上确认真实会话、读取空云库，以及上传并读回一条实际观看进度。读回出现过服务延迟；这是一份特定环境的历史证据，**不能扩大为所有账号和所有版本都可正常云同步**，手机端跨设备显示也没有因此完成验收。

后续正式版本没有反复发送短信或重新做真实账号写入。当前入口收纳在设置中，README 继续注明兼容性限制。Windows 凭据使用 DPAPI 加密，账号测试用合成响应，本地记录不充当官方云记录。

## 06 · macOS 历史排查：把“打不开”和“不能播放”分开

历史上曾提供 Mac 移植与多个 ARM64 修复候选。用户日志暴露出一组 Windows 没有的问题，调查必须按阶段区分。

### 目录正常，视频失败

搜索与榜单可用，说明不能直接把故障归到全部 API。调查转向媒体协议、源下载、解码器启动和 HTML 视频首帧。

一个候选改动使用本机回环 HTTP 媒体流，并校验 Host、Origin、路径和随机访问标记，避免把本机视频端点变成不受限的代理。跨平台共用链路可以在 Windows 上验证，但 Mac 自定义协议的具体失败原因不能只靠它唯一确认。

### 准备脚本中的解码器被系统终止

用户截图出现 `Killed: 9`，发生在安装前的 FFmpeg 自检，尚未进入客户端播放。

排查发现旧准备流程覆盖了供应商解码器签名，并在完整应用签名完成前执行自检。候选修复保留原解码器字节与签名，在新暂存副本中按层处理签名，全部检查通过才替换旧安装，失败保留旧版与诊断。

截图只证明进程被终止，不能唯一证明证书、隔离策略或签名缓存中的某一个分支。因此报告使用“定位到准备流程问题”和“修复候选”，没有说 Mac 实机已经全面通过。

### M102：解码器读取视频源失败

后来日志显示内容接口和播放信息已成功，FFmpeg 很快退出、输出字节为零。故障点在打开媒体源阶段，M102 只是分类，不能单凭这个代码认定是系统证书问题。

调整由 Electron/Chromium 请求 HTTPS 视频，继续正常校验证书与重定向白名单，再把受限的本机源交给 FFmpeg；支持所需范围请求。没有关闭 TLS 检查或导入系统证书。

### 为什么出现钥匙串密码提示

Mac 的 Electron 安全存储访问应用自己的钥匙串密钥时，系统可能弹出“Hongguo Safe Storage”授权。这是安全存储访问提示，不能直接等同于管理员提权，也不是播放视频必须申请整机权限。

候选修复让 Mac 游客只保存在当前进程内存，启动不自动解密旧游客或账号文件，从而避免游客浏览依赖钥匙串授权；没有删除旧条目。明确进入账号加密操作时，系统提示仍可能出现。

### 历史 Mac 结论的范围

Windows 上的共用源桥测试、Shell 流程替身、包资源与架构静态检查，都不等于在真实 Apple Silicon Mac 上运行了签名、解码器、Gatekeeper 和窗口操作。

当前公开仓库保留诊断代码，正式构建目标仍为 Windows x64。准备流程也没有把关闭全局 Gatekeeper、SIP、修改代理或证书当作修复手段。

## 07 · .14：搜索优化与系列剧归组

### 系列不能靠名字相似来判断

“某剧”和“某剧第二季”看起来有关，不代表任意同名作品都属于同一系列。原版选季流程使用官方合集成员信息。

开发沿原版选季调用链找到批量字段接口，读取合集编号、成员 ID、季顺序、剧名、封面、简介和集数。对没有确认的字段不盲目请求，也不靠标题猜关系。

### 不让系列整理拖慢首屏

搜索先显示已返回剧目，再异步整理系列成员。短期缓存和并发去重减少重复请求，但每个调用方得到独立快照，避免改一份列表影响另一个页面。

搜索失效、登录状态变化或新关键词出现时，旧请求不得生成新的有效游标。成员顺序遵循官方信息，不改变单剧相关性排序。

### 系列与选集连接起来

选集面板加入其他季，选择后获取那一季的真实目录和播放信息。每季保留独立剧目编号与观看进度，原合集元数据不能替代授权判断。

快速切季只允许最后一次有效请求提交；等待时点回正在播放的季，可以取消待切换并保留位置。

历史在线抽样验证过一个 13 季系列及其中两季目录，并在隐藏 Windows 窗口里实际切季播放。这个数量是当时样例，不是所有系列的固定规格。

## 08 · .15：排行榜按原版业务重新整理

原实现存在类别不全、续页模板不符，以及把不同选择规则当作同一种单选的问题。

重新调查后，排行入口与续页分开：首次读取计划，变化与翻页使用原版单元更新，并保留该榜单的选择状态、会话、offset 和 rank_version。首页推荐模板与排行模板也不能混用。

| 业务 | 关键发现 | 实现处理 |
| --- | --- | --- |
| 分类与子榜 | 原版还包含演员、系列剧等业务 | 按服务配置显示，不写死普通剧目布局逻辑 |
| 筛选 | 可多选、可取消单选、必选单选、至少一项多选 | 根据原枚举和互斥条件处理，验证选项属于当前配置 |
| 演员作品 | 普通用户 ID 与演员 ID 用途不同 | 使用对应演员编号查询真实作品，避免错误 ID 返回空列表 |
| 系列榜 | 展示的新季与跳转入口可能不是同一个 ID | 保留校验过的原入口，再通过系列信息切季 |
| 预约 | 零集不一定就是预约；演员条目也可能缺集数 | 结合明确预约与禁播字段判断，再核对最新详情 |

该阶段在线抽样覆盖当时六类、28 个子榜，演员作品和预约标记分别验证。分类和榜单数量会随服务变化，不能把历史数量当成永远固定的配置。

同时加入双击发现刷新，以及无边框／全屏切集时不自动浮出控件。主动移动鼠标或使用键盘仍能操作播放器。

**探索筛选当时还使用另一套分类接口。** 这套实现虽能返回数据，却后来被官方截图证明不是目标筛选页；2.3.3 做了进一步纠正，见下文。保留这一点，才能解释为什么“曾经通过测试”的代码仍需要重做。

## 09 · 2.3.0–2.3.2：统一风格与即时反馈

### 2.3.0：正式版界面整理

多个筛选菜单能同时打开，造成截图里的叠盖；旧箭头也与整体图标不一致。统一为互斥菜单组和细线 SVG 箭头，菜单按视口限制位置，空间不足向上展开，支持外部点击、Esc、滚动和窗口调整关闭。

播放器采用细进度轨道、统一按钮和留白。可点击区域没有随视觉轨道一起变得难点。导航、搜索、排行卡片、设置与选集使用统一颜色、圆角和字体层级，也兼顾窄窗口和减少动画偏好。

### 2.3.1：统一选择菜单与详情预览

清晰度展开后的蓝色高亮来自原生选择窗口，修改收起状态的 CSS 无法统一它。因此新增应用内菜单，同时替换播放器和设置中的同类选择框，支持键盘操作、互斥展开和视口约束。

详情与选集共用组件，封面、标题和追剧紧凑摆放，简介可展开，系列列表限制高度。删除用户指定的授权统计句，但保留每集锁定状态。

默认卡片入口先打开详情小窗。选择季或集只是选择，不提前启动视频、不写观看记录；用户点击播放后再进入播放器。预览关闭、重试和换季时，旧响应失效。

### 2.3.2：点第 41 集，立即高亮 41

旧高亮来自“已经开始播放的集数”，因此目标视频没加载好就仍显示旧集。修复把两个状态分开：

| 状态 | 表示什么 | 何时更新 |
| --- | --- | --- |
| 用户选择 | 接下来想看哪一集 | 点击后立即更新高亮、标题与计数 |
| 实际播放 | 哪一集已经提交给播放器 | 目标首帧就绪后交接 |
| 观看记录 | 真正看到了哪里 | 根据实际播放集与位置保存 |

快速选 41 → 42 → 43，只让最后一次生效；重复点击待加载的同一集不会重启。加载失败回到实际播放集，晚到的成功或失败都不能覆盖新选择。

隐藏专项用真实目录和视频，并人为延迟目标请求，验证“仍在加载时已经高亮目标集”。人工延迟用于验证响应时序，不冒充真实服务故障。

<a id="filter"></a>

## 10 · 2.3.3：由官方截图找回正确筛选逻辑

这是一次业务纠正，不只是调整外观。

旧接口 `/reading/bookapi/new_category/landing/v:version/` 返回另一套混合分类条件。用户提供的官方“筛选”截图包含体裁、主题、设定、背景、推荐、受众、时间、长度，布局与旧返回不同。

重新追踪请求和返回模型，确认对应 **`POST /reading/distribution/category/landpage/v1/`**。真实返回与截图逐项对应后，才替换原实现。

### 请求与分页也必须一起重做

新版选择不是逗号拼接的一串标签，而是“行类型 → 选项 ID 数组”。首次打开、更改条件、继续加载分别使用对应请求类型；分页保留本次筛选会话和服务下发的下一位置。

字符串 `0` 可能是有效选项，不能因为看起来像“空”就丢弃。选项 ID 必须在当前行内核验，相同 ID 出现在其他行不能随意跨用。

### 为什么不固定八行

当时真实返回出现过 7 或 8 行；漫剧可能增加画风、完结等条件，成为 9 或 10 行。长度也不是每个游客环境都下发。

因此名称、顺序、选项、默认值、单多选和数量上限都按当前配置处理。切体裁时清理已经消失的选项，收到新增行就显示。与旧接口的漫剧空结果不同，新接口在线样例得到真实漫剧和 AI 剧内容。

这些结果属于当时在线样例。动态处理能适应普通配置变化，但服务若改动整个协议，仍可能需要再次升级。

### 详情小窗尺寸稳定

用户指出加载前小、加载后突然变大。小窗改为从一开始使用最终布局：常规视口上限为约 700×780，窄窗口按可用空间缩小，只有主体内容滚动，底部操作保持稳定。

隐藏测试分别注入慢请求和失败，检查加载、正常、重试与系列切换的几何位置。一次检测发现旧入场动画还有 4 像素位移，随后去掉纵向动画，保留透明度过渡并复测。

## 11 · 2.3.4：去掉长条，增加一行一部剧

2.3.3 的筛选结构正确了，但每行横向滚动仍与用户要求不符。2.3.4 改为选项自动换行，左侧保留每行“全部”，配合轻分隔和留白；页头统一返回、标题、简短说明与重置入口。

这次只调整展示，不替换服务端条件、顺序、选择限制或分页。

目录新增一行一部剧，展示封面、名称、标签、集数和服务提供的简介。共享排列组件覆盖排行、探索、筛选、搜索、追剧、记录与演员作品，避免某个页面单独改变行为。

两种排列的顺序完全相同。默认仍为原卡片，设置可以保存列表；页面内临时切换不覆盖默认偏好。旧配置缺少新字段时采用兼容默认值，不重置既有播放设置。

专项验证覆盖普通与窄窗口、亮暗主题、筛选动态增删、快速选择、真实续页、列表右键追剧和设置保存。详情小窗继续保持尺寸稳定，播放和系列逻辑继续回归。

## 12 · 每一轮怎样验证，而不影响用户电脑

测试分成几层，每一层回答的问题不同。

| 层级 | 检查什么 | 不能推出什么 |
| --- | --- | --- |
| TypeScript 与构建 | 类型、导入、界面能否编译 | 不证明真实网络可用 |
| 离线契约／状态测试 | 受控返回、错误状态、缓存、授权和偏好处理 | 不证明真实登录和同步 |
| 在线接口抽样 | 原服务是否返回预期结构、分页与内容 | 不证明视频一定完成解码 |
| 隐藏静音桌面测试 | 实际界面操作、真实媒体帧、进度与布局 | 不证明用户桌面原生全屏已人工验收 |
| 人工查看测试截屏 | 重叠、溢出、配色、菜单和尺寸 | 不替代状态与网络验证 |
| 发布完整性校验 | ASAR 与最终源码／构建一致，资源和旧包哈希一致 | 不保证未来服务仍不变 |

音频解码计数大于零，表示有音频数据产生；测试保持静音，不是对外播放了声音。故障注入和延迟注入都单独说明，服务错误不会被伪装成已修复。

## 13 · 开源准备：整理源码，而不是把工作目录全部上传

首次开源使用独立目录，原工作项目和 Windows 发行程序保留。修改前备份包括源码、研究适配器与可运行工作版，清单记录版本、范围和逐文件校验。

### 公开与排除

| 公开的部分 | 排除的部分 |
| --- | --- |
| 原创 React/Electron 源码 | 原 APK 与反编译第三方源码 |
| 原创 Java JNI 回调和 worker | APK 专有库与 SDK 配置 |
| 合成测试与公开数据结构 | 捕获响应、真实账号和设备资料 |
| 构建和检查脚本 | 运行二进制、视频、封面与官方标识 |
| 中文文档、MIT 与第三方说明 | 原始日志、截图和现有完整成品包 |

测试样本改用合成目录，图像集成改为可选本地输入。适配器去掉研究入口、私人路径和捕获状态，保留运行需要的回调。新增原创标识，避免直接发布官方图标。

### 构建脚本也做实际检查

新资源准备脚本编译适配器、生成 Java 运行环境、检查 FFmpeg，并清空身份相关配置项。测试发现 Windows PowerShell 给 JSON 数组附加属性，可能把配置写成 `{ value, Count }` 对象；重建纯数组后修正，并执行新适配器在线检查。

在线检查通过新游客注册、发现、搜索、详情与视频信息请求。这次没有运行完整画面解码验收，因此没有把“视频信息返回成功”写成“公开视频播放通过”。

依赖审计结果另外记录在安全文档：当时 8 项中等风险来自同一 `sprintf-js` 开发依赖链问题，0 高风险、0 严重风险。没有可验证修复版时，不使用强制自动降级制造一个表面无告警的环境。

### 上传后的核对

首次发布保留 GitHub 初始提交，使用期望分支 SHA 更新 main，没有强制覆盖历史。111 个公开文件逐个与审计后的 Git blob 校验一致，本地工作区与远端一致。

仓库增加源码 CI 配置，但首次发布 API 没返回工作流运行记录；因此只说配置已经存在，不说云端已经测试通过。

这次 README 重写继续采用先备份、后编辑、再检查和发布的方式。首页面向普通读者，完整复盘放在本文，文档横幅使用原创 SVG，不上传官方素材或私人截图。

## 14 · 当前边界与后续方向

项目已经形成完整的 Windows 短剧浏览和播放交互链，但几件事仍需要持续独立验证：

1. **账号兼容性**：真实短信登录、挑战状态、云读取和上传需在明确授权的真实账号环境中检查，不能靠本地数据代替。
2. **官方变化**：分类配置可以动态适配，协议、签名 SDK 或模型结构改变则需要重新调查。
3. **macOS 实机**：签名、系统策略、ARM64 解码器和原生窗口需要 Mac 设备上的真实结果；Windows 成功不能代替。
4. **运行资源与分发**：公开源码需要自行准备第三方文件，完整二进制发布仍需分别处理依赖和内容许可。
5. **依赖维护**：修复版出现后再更新锁文件，运行与变更相称的检查，避免不明原因强制替换整个构建链。

开发中反复出现的经验是：**点击反馈、网络等待、真正开始播放和保存观看记录，应当各自表达清楚；原版业务的证据，也应当与客户端展示方式分开。** 这样既能让操作更顺手，也能避免界面已经显示成功、实际状态却没有完成的情况。
